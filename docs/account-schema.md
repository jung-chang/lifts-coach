# Account and sharing schema contract

Implementation contract for the approved multi-user extension. Migration `0004_accounts_community.sql` introduces email-linked accounts, their single profiles, sharing decisions and rebuildable training projections. The migration is applied only by the deployment workflow; local implementation does not imply production migration or public beta readiness. Keep the protected product specification unchanged.

The later community-feed request simplifies the audience to all active admitted accounts. Follow the [community feed plan](community-feed-plan.md). No connection graph or separate community-membership table is required initially; publications drive both the feed and shared profile history.

## Naming and ownership

Use **accounts** consistently for the persisted owner. Community and People are navigation labels, not additional identity tables. Use `account_id` for ownership references everywhere; `id` is the entity's own identifier. Do not alternate between `user_id`, `person_id` and `owner_id` for the same relationship.

Use application-generated immutable UUIDs as account keys. Email is a unique login/contact attribute, not a primary key, URL, IndexedDB database name or foreign key. The account ID remains stable through approved email or identity changes. Every account-owned row has a real foreign key, with compound keys for owner-local IDs. Client-supplied workout IDs are unique only within their account.

**Exactly one account to one profile.** Use `profiles.account_id` as both its primary key and a foreign key to `accounts.id`, with `ON DELETE CASCADE`. There is no independent profile primary key, multiple-profile feature or separately owned social identity. `public_id` is only a unique external lookup alias for the same profile. Private coaching preferences are account-owned settings, not an additional profile entity.

The shared primary key prevents multiple profiles per account; the foreign key prevents orphan profiles. Neither constraint alone requires every account to have a profile. Ensure that existence through one transactional provisioning operation that creates the account, its profile and sharing settings together, including during migration. Roll back the whole operation on failure. Do not expose independent profile creation/deletion; disable the account without dropping its profile, and delete both through account deletion. Test provisioning failure, concurrent first login, missing legacy profiles and cascade deletion explicitly.

## Core tables

| Table              | Key and important fields                                                                                                                                                                                           | Responsibility                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `accounts`         | `id` PK; `email`; `email_normalized` UNIQUE NOT NULL; `access_issuer`; `access_subject`; `status`; `coach_enabled`; `created_at`; `updated_at`; UNIQUE (`access_issuer`, `access_subject`)                         | Private identity, account lifecycle and server entitlements                                                   |
| `profiles`         | `account_id` PK/FK → accounts ON DELETE CASCADE; `public_id` UNIQUE NOT NULL; `display_name`; `training_timezone`; `created_at`; `updated_at`                                                                      | Exactly one profile per account; shared responses expose only approved fields                                 |
| `sharing_settings` | `account_id` PK/FK → accounts; `summary_enabled` default false; `auto_publish_workouts` default false; `workout_sharing_enabled_at` nullable; `audience_acknowledged_at` nullable; `policy_revision`; `updated_at` | Separate all-history summary consent and prospective automatic workout sharing after audience acknowledgement |
| `account_state`    | `account_id` PK/FK → accounts; existing revision, payload and device/operation metadata                                                                                                                            | Canonical private revisioned training document                                                                |
| `state_chunks`     | PK (`account_id`, `chunk_index`); FK → account_state                                                                                                                                                               | Storage of the same canonical document across bounded rows                                                    |
| `sync_receipts`    | PK (`account_id`, `operation_id`); FK → accounts; existing revision/fingerprint/time                                                                                                                               | Idempotency per owner                                                                                         |
| `coach_requests`   | PK (`account_id`, `id`); FK → accounts; `created_at`                                                                                                                                                               | Per-account request limits; no prompts or responses                                                           |

Initially keep one Access issuer/subject pair on the account. A separate identity-provider table is unnecessary for this beta. Introduce `account_identities` only if supporting multiple login identities per account becomes a real requirement. Keep private Coach preferences in the existing versioned document; do not duplicate them in the social profile.

`status` is a constrained `active` or `disabled` value. Boolean flags are constrained 0/1 integers. Store timestamps uniformly as UTC ISO 8601 text; local training dates are explicit `YYYY-MM-DD` values with a validated IANA timezone. Specify NOT NULL and defaults explicitly rather than depending on SQLite permissiveness. Use a single documented email-normalization function: trim surrounding whitespace and lowercase for this application's case-insensitive login policy; retain the authenticated spelling separately. Never strip dots, plus suffixes or apply provider-specific alias rules.

## Resolving Cloudflare Access identity

Accept identity and email only from the application JWT after checking signature, configured issuer/audience, expiry and token timing. Require a nonempty human subject and valid email claim. Do not trust a plain email header, query parameter or form value. Missing claims fail closed. Keep local development identities explicitly restricted to loopback and separate from production account records.

Resolve the validated (`issuer`, `subject`) to one active account. New identities can create an account only through the configured beta admission flow. Account creation and profile/settings initialization must be atomic and tolerate concurrent first requests through unique constraints.

The email links the account to the address admitted by Access. It does not authorize automatic account merges. A new subject whose email collides with an existing account, or an email change on an existing subject, requires an explicit verified recovery/change process. Do not overwrite another account's email, create a duplicate account or transfer history automatically. A disabled account stays disabled even when an otherwise valid JWT is presented. Check application account status independently of the Access allow policy.

Cloudflare documents the human token's email as authenticated by the identity provider, and notes that the subject may change when a user is removed and re-added to the organization. This is why database ownership must outlive the auth subject. See [application token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/) and [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/). These are authentication inputs, not public profile fields. Never persist JWTs, cookies, session tokens or provider secrets in these tables.

## Community visibility and publication

| Table                  | Keys and constraints                                                                                                                           | Responsibility                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `account_blocks`       | PK (`account_id`, `blocked_account_id`), both FKs; CHECK unequal; `created_at`                                                                 | Directed block enforcing shared-access denial in both directions                                        |
| `workout_visibility`   | PK (`account_id`, `workout_id`); FK account_id → accounts; `visibility` CHECK private/community; `decision_revision`; `updated_at`             | Durable explicit decision, including private overrides for active or finished workouts                  |
| `workout_publications` | PK (`account_id`, `workout_id`); compound FK → training_workouts; `id` UNIQUE NOT NULL; `activity_at`; `published_at`; optional `shared_title` | One stable publication identity/order per workout; current visibility determines whether it can be read |

Every active admitted account is a community member. Omit `connections`, social invitations and community-membership tables for this version. Admission invitations, if needed, belong to account admission rather than feed relationships. A block is stored in its initiating direction but denies shared reads in either direction, including direct profile/workout links and comparisons. Disabled accounts have no community access regardless of publication rows.

Each row has one responsibility: account-level defaults and summary consent in `sharing_settings`, explicit per-workout decisions in `workout_visibility`, stable feed identity in `workout_publications`. Do not store visibility on every set or duplicate workout contents in feed records. Only authenticated community/private visibility exists initially. Keep private overrides even without publication rows; joining or changing defaults must not publish old/private workouts accidentally.

Use revision-checked, account-scoped visibility operations. Initialize a future workout's decision from the acknowledged current sharing policy; an offline publication intent must reference that policy revision. A newer private decision or policy disablement wins over stale queued publication, with an explicit conflict/review when needed. Enabling automatic sharing records an effective start time and never backfills older sessions. A private backup's settings or workout payload cannot itself grant publication access.

Publish only after the finished source is synchronized and contains completed working sets. Enforce the owner/workout key for retry deduplication. Retain a hidden workout's publication metadata while `workout_visibility` denies access, so hide/re-share preserves its original ID and `activity_at`. Corrections update the current projection without changing activity order. Actual source deletion removes its publication; retain a private visibility tombstone until stale writes can no longer revive it. Account deletion clears all of these records.

## Queryable training data

Keep `account_state` as the sole editable source of truth initially so this work does not require a simultaneous rewrite of offline sync and backup. Add **private, rebuildable relational projections** of finished training for efficient summary queries. They are not independently editable and are not public tables.

| Table                       | Key and fields                                                                                                                                                              | Purpose                                                                                                      |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `training_projection_state` | `account_id` PK/FK → accounts; `source_revision`; `built_at`                                                                                                                | One complete, committed projection revision per account                                                      |
| `training_workouts`         | PK (`account_id`, `workout_id`); FK → projection state; `started_at`; `completed_at`; `training_date`; `training_timezone`; `source_revision`                               | Finished sessions and stable calendar attribution                                                            |
| `training_sets`             | PK (`account_id`, `workout_id`, `exercise_instance_id`, `set_id`); compound FK → training_workouts; `exercise_id`; `load_mode`; `weight_lb`; `reps`; `kind`; `completed_at` | Completed sets with canonical exercise/load semantics; existing set IDs may repeat across exercise instances |

Only finished workouts and completed sets enter these projections. Keep `kind` so shared workout detail can distinguish warm-ups; volume and lift queries explicitly filter working sets. Constrain kind/load-mode enums and nonnegative finite load/rep values, consistent with domain validation. Include exercise-instance identity because the same exercise may occur twice in one session. Built-in `exercise_id` refers to the versioned catalog; custom identities are scoped by `account_id` and never matched by display name. No FK to a nonexistent global custom-exercise table.

Do not duplicate arbitrary workout titles, notes, feelings, Coach data or the full JSON document into these tables. Shared workout titles can use a neutral date-based label initially; an optional explicitly approved title belongs on `workout_publications.shared_title`. Only approved exercise labels are returned in feed/detail DTOs; custom display names require the same shared-content preview. Keep other fields behind explicit domain validation and sharing scope.

Compute weekly set counts and qualified lift records from these same projection rows. Avoid separate stored `shared_summaries`, volume totals and personal-record tables until measured query costs justify a cache. This keeps corrections, unsharing and deletion from having to reconcile several competing totals. If caching becomes necessary, every derived value must carry its account, source revision, definition version and sharing scope.

Rebuild projections transactionally after an accepted private sync. Keep the previous committed projection until a complete newer one exists, but expose comparisons/feed items only when its source revision matches current account state. If rebuilding is asynchronous, show summaries as updating; never use an outdated record after source deletion or correction. New requests must also check current account status, block state and sharing settings/visibility. A projection's existence is never permission to read it.

Reconcile projection rows by stable owner/workout/set keys. Preserve explicit visibility and publication metadata across ordinary corrections. Restore/import hides existing publications, resets per-workout visibility to private and disables automatic/summary publication pending review. Delete projections, blocks, visibility and publications on account deletion using declared FK actions and a tested deletion transaction. Do not let a cascade during an ordinary projection refresh accidentally erase valid sharing choices.

## Indexes, migrations and tests

Index actual access paths: `training_workouts(account_id, training_date)`, `training_sets(account_id, exercise_id, load_mode, kind)`, `coach_requests(account_id, created_at)`, and `sync_receipts(created_at)` for retention. The feed needs `workout_publications(activity_at DESC, id DESC)` and profile history needs `(account_id, activity_at DESC, id DESC)`. Add a reverse-account index for blocks. Compound primary keys already cover their leading prefixes; do not add duplicate indexes. Keep unique email and issuer/subject indexes as declared constraints. Use bounded cursor pagination over `(activity_at, id)` and bounded comparison date ranges at the API layer.

`worker/schema.ts` and ordered SQL migrations must describe the same schema, constraints, indexes and foreign keys. Use explicit typed repository functions for account resolution, state sync, sharing and comparisons; do not scatter loosely related ownership queries throughout route handlers. Keep authorization predicates central and test them with two accounts.

Do not edit already-applied migrations. Introduce forward migrations that preserve the current account-scoped state, chunks, receipts and request rows. In particular, replace the ambiguous `account_state.id` ownership column with `account_id` and reference `accounts.id`. Back up before applying changes. Existing `access:<hash>` keys cannot reveal the email or original subject: create an explicit legacy mapping during verified sign-in/recovery, prove ownership using the current subject-derived key, and migrate related rows transactionally. Never guess identity from workout/profile contents or reuse the historical destructive reset migration.

Verify fresh-database creation and upgrade from populated synthetic legacy data; duplicate first logins; email/identity collisions; disabled accounts; FK orphan rejection; cross-account duplicate workout IDs; both block directions and self-block constraints; account deletion; and projection rebuilds after corrections, restore and sync retries. Feed checks cover one publication per workout, private overrides surviving retries, no historical backfill, stable activity timestamps, cursor ties, delayed offline completion, hide/re-share, deletion tombstones and restore without republishing. Confirm idempotency, row/chunk limits, account-bound browser migration and no unauthorized reads/writes. Retain the pinned toolchain and the repository's full checks before implementation is published. This design document does not apply a migration or change production Access policy.
